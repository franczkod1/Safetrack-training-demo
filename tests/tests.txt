# Tests

## Test 1 - Print preparation stores a central SafeTrack document [sanity]
Viewport: desktop
Covers: POST /api/documents/prepare, POST /api/documents/:id/snapshot, central ST-DOC allocation, four-column confirmation layout, print-save acknowledgement
Description: Verifies group printing creates a central document record before the system print flow and preserves the signature-friendly layout.

Steps:
1. Open "Unterweisungen", select one broadly applicable training, choose "Mitarbeitende zuweisen", select several employees, enter the instructor fields, and open the confirmation preview
2. Verify the participant table contains only "Mitarbeitende Person", "PNr.", "Tätigkeit", and "Unterschrift", then choose "Drucken"
3. Return from the print flow and inspect the save confirmation

Expected: The printed confirmation has no participant Datum column, signature cells are wide, the ST-DOC identifier is centrally allocated, and a "Dokument erfolgreich gespeichert und druckbereit" acknowledgement appears.

## Test 2 - Documents menu is central and exposes bulk upload
Viewport: desktop
Covers: GET /api/documents, POST /api/documents/:id/printed, central document registry, multi-file upload entry point, document status
Description: Verifies acknowledging a print opens the server-backed document register and exposes the new independent upload control.

Steps:
1. Continue from a prepared print acknowledgement and choose "Druck bestätigt – Dokumente öffnen"
2. Inspect the Documents view and the created document row
3. Inspect the upload control

Expected: The document appears with status "Gedruckt – Rückupload ausstehend", a standalone "Dokumente hochladen" button is visible, and its file control accepts multiple PDF/JPG/PNG files.

## Test 3 - Document detail blocks completion before a verified return
Viewport: desktop
Covers: GET /api/documents/:id, GET /api/documents/:id/snapshot-url, leader-review guardrail, review status presentation
Description: Verifies a printed document remains review-safe until a signed return has been automatically checked.

Steps:
1. Open a printed document from "Dokumente"
2. Inspect the saved-document action and review area
3. Inspect the "Prüfen & abschließen" button before any matched return upload exists

Expected: The saved document can be opened, the document shows its central metadata and participants, and "Prüfen & abschließen" is disabled until a matched uploaded document has reached leader review.

## Test 4 - Employee profile reads central documented completions
Viewport: desktop
Covers: GET /api/employees/:pnr/completions, employee profile completion synchronization, signed document link
Description: Verifies employee profiles query the central completion store and provide a document area without breaking the existing training profile.

Steps:
1. Open "Mitarbeitende", expand an area and job group, then open an employee profile
2. Inspect the normal training list and the lower profile area
3. Close and reopen the employee profile

Expected: The employee profile remains usable, central completion lookup succeeds without frontend or network errors, and when documented completions exist they are shown under "Dokumentierte Abschlüsse" with a "Dokument öffnen" action.

## Test 5 - Mobile multilingual and document UI remain responsive
Viewport: mobile
Covers: mobile navigation, Arabic RTL, Documents dialog, PNr-#### format, horizontal overflow prevention, existing print CSS regression
Description: Verifies the backend upgrade does not regress mobile, RTL, personnel identifiers, or document navigation.

Steps:
1. Open the mobile menu, switch to Arabic, then open "Mitarbeitende" and inspect a PNr. value
2. Open and close an employee profile, then open "Dokumente"
3. Inspect the Documents header, upload button, and page width

Expected: Arabic RTL remains active, personnel identifiers retain the PNr-#### format, Documents is usable on mobile, the upload button remains reachable, and the page has no horizontal scrolling.
