# Tests

## Test 1 - Print, acknowledge, and open the central document register [sanity]
Viewport: desktop
Covers: POST /api/documents/prepare, POST /api/documents/:id/snapshot, POST /api/documents/:id/printed, GET /api/documents, central ST-DOC allocation, four-column print layout, document status, bulk upload entry point
Description: Verifies one complete print workflow creates and acknowledges a central document without relying on another test's state.

Steps:
1. Open "Unterweisungen", select one broadly applicable training, choose "Mitarbeitende zuweisen", select several employees, enter the instructor fields, and open the confirmation preview
2. Verify the participant table contains only "Mitarbeitende Person", "PNr.", "Tätigkeit", and "Unterschrift", choose "Drucken", then return from the print flow
3. Choose "Druck bestätigt – Dokumente öffnen" and inspect the created document row and the Documents header

Expected: The confirmation has no participant Datum column, the Unterschrift column is wide, a central ST-DOC identifier is allocated, the document appears with status "Gedruckt – Rückupload ausstehend", and a standalone "Dokumente hochladen" control is visible and supports multiple PDF/JPG/PNG files.

## Test 2 - Newly printed document blocks completion before a verified return
Viewport: desktop
Covers: GET /api/documents/:id, GET /api/documents/:id/snapshot-url, central document detail, saved print snapshot, leader-review guardrail
Description: Verifies the guardrail and saved snapshot using a document created inside this same independent test.

Steps:
1. Create a group confirmation from "Unterweisungen", select at least one matching employee, open the preview, choose "Drucken", then acknowledge with "Druck bestätigt – Dokumente öffnen"
2. Open the document just created in the Documents list and inspect its metadata and participant list
3. Choose "Gespeichertes Dokument öffnen", confirm the saved document opens, return to the detail, and inspect "Prüfen & abschließen"

Expected: The document detail shows its ST-DOC, training metadata and participants; the centrally saved print snapshot can be opened; and "Prüfen & abschließen" remains disabled because no automatically checked signed return has been uploaded.

## Test 3 - Signed return is matched, reviewed, completed, and visible on the employee [full-pipeline]
Viewport: desktop
Covers: POST /api/uploads/store, POST /api/uploads/:id/analyze, POST /api/uploads/:id/finalize, POST /api/documents/:id/complete, GET /api/documents/:id/file-url, GET /api/employees/:pnr/completions, QR/OCR comparison, leader approval, completion assignment, employee profile document link
Description: Runs the real v0.21 signed-return backend pipeline using the QA-only synthetic paper return. The QA helper is only visible when AppDeploy runs with its internal qa_ key and is absent in normal SafeTrack use.

Steps:
1. Create and print one group confirmation with one matching employee, note that employee's name and PNr., then choose "Druck bestätigt – Dokumente öffnen"
2. In Documents choose "QA Rücklauf simulieren" and wait until the created document changes to "Prüfung durch Führungskraft erforderlich"; open it and inspect "Automatische Prüfung"
3. Choose "Prüfen & abschließen", confirm the action, verify the document becomes green "Abgeschlossen – Mitarbeitenden zugeordnet", open the signed document, then open the noted employee profile and verify "Dokumentierte Abschlüsse" contains this ST-DOC with a "Dokument öffnen" action

Expected: The synthetic signed return passes through storage and real OCR/QR matching, requires leader approval, becomes green only after approval, the signed file is retrievable, the employee's training completion is synchronized, and the same signed ST-DOC is directly accessible from that employee profile.

## Test 4 - Mobile multilingual and Documents UI remain responsive
Viewport: mobile
Covers: GET /api/documents, GET /api/employees/:pnr/completions, mobile navigation, Arabic RTL, Documents dialog, PNr-#### format, horizontal overflow prevention
Description: Verifies the backend upgrade and profile refresh fix do not regress mobile, RTL, personnel identifiers, or document navigation.

Steps:
1. Switch the language selector to Arabic, navigate to "Mitarbeitende", expand an area and job group, and inspect a PNr. value
2. Open and close one employee profile, then open "Dokumente"
3. Inspect the Documents header, "Dokumente hochladen" control, and full page width

Expected: Arabic RTL remains active, personnel identifiers retain the PNr-#### format, employee profile lookup succeeds, Documents is usable on mobile, the upload control is reachable, and the page has no horizontal scrolling.
